# ข้อกำหนดซอฟต์แวร์ KooKid

สถานะ: Proposed baseline v0.1 • 3 พฤศจิกายน 2569

## เป้าหมายและสมมติฐาน

ช่วยสำนักงานบัญชีลดเวลารวมในการร่างและตรวจงาน โดยเก็บความรู้ที่ผู้เชี่ยวชาญอนุมัติและหลักฐานการตรวจ โครงการทุน 6 เดือนครอบคลุมสัมภาษณ์ 10 แห่ง ทดลอง 1–2 แห่ง และต้นแบบชั้นความรู้กับชั้นงาน ตัวเลขด้านประสิทธิภาพด้านล่างเป็นเป้าหมายเสนอใหม่ ต้องยืนยันหลังเก็บ baseline ไม่ใช่ผลที่พิสูจน์แล้ว

ผู้ซื้อคือเจ้าของสำนักงาน กลุ่มแรกตามข้อเสนอคือสำนักงาน 20–30 คนในภาคเหนือ เริ่มทดลองกับผู้ใช้จำนวนน้อยก่อน ขอบเขตงานเสนอเริ่มจากร่างคำตอบขอเอกสารเพิ่มและตรวจรายการเอกสารตาม checklist ไม่คำนวณภาษี ยื่นแบบ หรือให้คำวินิจฉัยภาษีอัตโนมัติ

## บทบาท

| บทบาท | สิทธิ์หลัก |
|---|---|
| Staff | สร้าง/แก้งานตนเอง ดูความรู้ที่อนุมัติ ส่งตรวจ เสนอความรู้ |
| Reviewer | ดูงานที่ได้รับมอบหมาย ตรวจ แก้ ส่งกลับ อนุมัติงาน อนุมัติความรู้หากได้รับสิทธิ์ curator |
| Admin | เชิญ/ระงับสมาชิก ตั้งประเภทงาน checklist ผู้ตรวจ นโยบายข้อมูล และดูรายงาน |

Admin ไม่ได้รับสิทธิ์อนุมัติงานโดยอัตโนมัติ ผู้สร้างงานห้ามอนุมัติงานตนเองใน pilot ผู้เชี่ยวชาญภาษีรับผิดชอบความรู้ ไม่ใช่ AI

## ขอบเขต

P0: สมาชิกและแยกสำนักงาน ฐานความรู้ที่มีรุ่นและวันมีผล ค้น/ร่างพร้อมอ้างอิง งานและการตรวจ audit log และการเก็บผลทดลอง

P1: Dashboard แยกประเภทงาน รายงานรายเดือน CSV และการแจ้งเตือน ส่วน dashboard ในทุนเป็นรายงาน/ตัวอย่างจากข้อมูล pilot

นอกขอบเขต: ฝึก foundation model, เชื่อมบัญชีจริง, ยื่นภาษี, ส่งข้อความลูกค้าอัตโนมัติ, billing, mobile app, OCR เอกสารสแกน, แชร์เนื้อหาหรือคะแนนข้ามสำนักงาน

## State และกติกา

Task: draft → in_review → approved หรือ returned → in_review. การสร้างร่าง AI ใหม่ทำได้เฉพาะ draft/returned และต้องไม่ล้างประวัติเดิม รุ่น approved เป็น immutable. Revision เป็นหน่วยอนุมัติ ใช้ optimistic concurrency (version) ป้องกันผู้ตรวจอนุมัติร่างที่ถูกแก้ไปแล้ว งาน AI ล้มเหลวยังคงข้อมูลที่กรอกและ retry ได้ ไม่สร้างร่างซ้ำจาก request เดิม

Knowledge: draft → pending → approved/rejected → archived. การแทนที่/หมดอายุรุ่นเก่าไม่แก้หลักฐานของงานที่เคยอ้างอิง

## Nonfunctional requirements เสนอสำหรับ pilot

| ID | เป้าหมาย | วิธีตรวจ |
|---|---|---|
| NFR01 | แยก tenant ทุกตาราง/ไฟล์/vector และตรวจสิทธิ์ฝั่ง server | integration test A/B, non-member, suspended และ direct API |
| NFR02 | p95 หน้ารายการ < 2 วินาที; AI response เป้าหมาย < 30 วินาทีบนชุด pilot | ทดสอบ 10 sessions พร้อมกัน แยก latency provider; timeout 60 วินาทีและ retry อย่างปลอดภัย |
| NFR03 | TLS, secret ฝั่ง server, private storage, ไม่ log ข้อมูลลูกค้าเต็ม | ตรวจ configuration และตัวอย่าง log; key ไม่อยู่ใน browser bundle |
| NFR04 | สำรองรายวัน เป้าหมาย RPO 24h/RTO 1 วัน | ทดลอง restore ฐานข้อมูลและไฟล์ก่อน pilot; ต้องเลือกแพ็กเกจที่รองรับ |
| NFR05 | ภาษาไทย desktop/mobile 375px+, keyboard และ label ครบ | ตรวจ Chrome/Edge, keyboard, contrast และ no overflow |
| NFR06 | งบ AI จำกัดต่อสำนักงาน และแจ้งเตือนก่อนถึงโควตา | จำลอง rate limit, quota และ provider outage; ไม่ retry ไม่จำกัด |

## Data และข้อจำกัด

ข้อมูลลูกค้าเป็นข้อมูลลับ ต้องกำหนดผู้ควบคุม/ผู้ประมวลผล เงื่อนไขผู้ให้บริการ retention และวิธีลบก่อน pilot เริ่มด้วยข้อมูลสังเคราะห์/ปิดบังและการตรวจคน การปิดบังด้วย regex อย่างเดียวไม่ครอบคลุมข้อมูลส่วนบุคคลทั้งหมด

เอกสารที่ค้นได้เป็นข้อมูลอ้างอิง ห้ามทำตามคำสั่งที่ฝังในเอกสาร (prompt injection) และห้ามให้โมเดลเรียก tool ที่ส่งออกหรือแก้ข้อมูลใน MVP. Citation ไม่ใช่หลักฐานว่าคำตอบถูกต้อง ต้องตรวจโดยผู้เชี่ยวชาญ
