# แผนส่งมอบและเกณฑ์ตัดสินใจ

## แผน 6 เดือน

| ช่วง | งาน | Exit criteria |
|---|---|---|
| เดือน 1–2 | สัมภาษณ์ 10 แห่ง เก็บ baseline เลือกงาน 2 แบบ ทำ mockup และหาผู้เชี่ยวชาญ | มีสำนักงานร่วม pilot อย่างน้อย 1 แห่ง ยืนยันโจทย์ ผู้ตรวจ และเงื่อนไขข้อมูล |
| เดือน 2–3 | Identity/tenant, ฐานความรู้, workflow งานและ review | เดินงานครบหนึ่งรอบด้วยข้อมูลสังเคราะห์ แยก tenant ผ่าน integration test |
| เดือน 3–4 | ingestion, RAG, citation, audit และชุด eval | ต้นแบบชั้น 1/2 ทำงานจริง ผ่านผู้เชี่ยวชาญและกรณี no-source/provider failure |
| เดือน 4–6 | pilot 1–2 แห่ง เก็บเวลาและคุณภาพ แสดง report | ผลเทียบ baseline, สัมภาษณ์ราคา และบันทึกข้อจำกัด/ข้อผิดพลาด |
| เดือน 5–6 | แผนธุรกิจและแผนพัฒนารอบต่อไป | ส่งมอบต้นแบบ ผลทดสอบ แผนต้นทุน และข้อเสนอ go/pivot/stop |

## วิธีประเมิน

1. ทำชุดประเมินเริ่มต้นเสนอ 50 กรณี: คำถามปกติ ข้อมูลไม่พอ เอกสารขัดกัน/หมดอายุ prompt injection และแหล่งอ้างอิงปลอม ให้ผู้เชี่ยวชาญกำหนดคำตอบ/เกณฑ์และระดับความรุนแรงก่อนทดสอบ
2. แยก development cases กับ holdout; ไม่ปรับ prompt โดยดู holdout ซ้ำจนคะแนนดี เก็บ model/prompt/knowledge version ทุก run
3. เปรียบเทียบงานระดับยากใกล้กันแบบมี/ไม่มีระบบ สลับลำดับเพื่อลด learning effect เก็บเวลา active ของผู้ร่างและผู้ตรวจรวมกัน รวมเวลาป้อนความรู้และอบรมแยกต่างหาก
4. เป้าหมายเสนอ: ลด median active time ≥20% โดยอัตราข้อผิดพลาดสาระสำคัญไม่เพิ่ม และไม่พบข้อผิดพลาดร้ายแรงที่หลุดอนุมัติในชุดทดสอบ ผล pilot ขนาดเล็กไม่รับรองความปลอดภัยทั้งตลาด
5. วัดความเต็มใจจ่ายด้วยราคา/แพ็กเกจชัดเจน บันทึกผู้มีอำนาจซื้อ การตอบรับทดลองไม่เท่ากับยอมซื้อ

## ต้นทุนและความเป็นไปได้

งบต้นแบบในข้อเสนอ 30,000 บาทรวม API/cloud ระหว่างทดสอบ เหมาะกับต้นแบบจำกัดขอบเขตหากทีมทำเอง ไม่ควรตีความว่าเพียงพอจ้างพัฒนาระบบ production ทั้งหมด ต้องแจกแจงแรงงานทีมและสิ่งที่จ้างเพิ่มแยกจากเงินทุน

สูตรคำนวณต่อสำนักงาน/เดือน:

`AI = งาน × (input_tokens × ราคา input + output_tokens × ราคา output) + embedding + retries`

`ต้นทุนบริการ = AI + ส่วนแบ่ง hosting/database/storage/backup + support hours × ต้นทุนแรงงาน + ค่าอัปเดตความรู้`

`gross margin = (รายได้ - ต้นทุนบริการ) / รายได้`

ราคา token ต้องแปลงหน่วยตาม provider; เก็บ usage จริงก่อนตั้งแพ็กเกจ 1,500–3,000 บาท ไม่ใช้ unlimited. ปีที่ 3 มี 150 สำนักงาน × 2,000 × 12 = 3.6 ล้านบาทเป็น annualized revenue เมื่อครบ 150 แห่ง ไม่ใช่รายได้ทั้งปีหากเพิ่งครบสิ้นปี

## ความเสี่ยงและจุดตัดสินใจ

| เรื่อง | การจัดการ/หลักฐานที่ต้องมี |
|---|---|
| เพิ่มภาระรุ่นพี่ | วัดเวลารวมและลด form ที่ไม่เกิดประโยชน์ หยุดขยายหากประหยัดเวลาไม่ได้ |
| คำตอบผิดแต่คะแนนสูง | rubric, independent review, severity และ sample size; ไม่ปลด human review |
| ใช้งานนอกระบบ | สัมภาษณ์พฤติกรรมจริง ระบบควบคุมได้เฉพาะงานที่เข้ามา |
| ความลับลูกค้า | เริ่ม synthetic, ตรวจ provider terms/region/retention และนโยบายสำนักงานก่อน real data |
| งบไม่พอ | ทำ text-first และ report ขั้นพื้นฐานก่อน upload/OCR/integration |
| ความรู้หมดอายุ | เจ้าของเนื้อหา วันมีผล วันทบทวน และ archive; ผู้เชี่ยวชาญยืนยันฉบับใช้งาน |

ต้องยืนยันกับเจ้าของโครงการ: ประเภทงาน pilot, ผู้เชี่ยวชาญและผู้ตรวจ, แรงงานทีม, ช่องทาง web, ระยะเก็บข้อมูล, การอนุญาตส่งข้อมูล AI, hosting region, ราคา และเกณฑ์ go/no-go. ก่อน production เพิ่ม penetration/security review, monitoring, restore drill, incident process และยืนยันเงื่อนไขข้อมูลกับผู้เกี่ยวข้อง

## Demo เทียบกับ MVP

เดโม: navigation, form validation, role simulation, task states, checklist, score, knowledge approval, metrics และ audit ใน memory

ยังต้องพัฒนา: login จริง, tenant isolation, persistent database, upload/parser, LLM/RAG, authorization, concurrent transactions, backup, quotas และ export/delete. ห้ามใช้เดโมเพื่อรับข้อมูลลูกค้าจริง
